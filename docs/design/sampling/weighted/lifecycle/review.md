## Confirmed issue

**P2 — a permanently trimmed recorder can be re-enabled through the existing public recorder controls.** `SamplingStatus::register_recorder` installs `Dial9Handle::disable_callback` (`/tmp/dial9-manual-sampling-spike/dial9-sampling/src/lib.rs:391`). That callback invokes ordinary `SharedState::disable` (`/tmp/dial9-manual-sampling-spike/dial9-core/src/handle.rs:224`, specifically line 231), which transitions Enabled → Disabled and permits `Dial9Handle::enable`/`Recorder::enable` to transition back to Enabled (`/tmp/dial9-manual-sampling-spike/dial9-core/src/shared_state.rs:116`, `/tmp/dial9-manual-sampling-spike/dial9-core/src/recording.rs:188`).

Reachable trigger: application code retains a recorder/handle, a background census trims the process, then an existing profiling controller calls `enable()`. The protocol has already made this process Carrier and only applies trims to Active members (`/tmp/dial9-manual-sampling-spike/dial9-sampling/src/protocol/engine.rs:896`); the one-shot registration callback has already been consumed (`/tmp/dial9-manual-sampling-spike/dial9-sampling/src/registration.rs:15`). Recording resumes while the census permanently classifies it as non-recording, and future roster trims do not turn it off again.

Isolated executed reproduction: `/tmp/dial9-sampling-review-lifecycle/reenable.rs` constructs a real recorder, invokes its stop callback, asserts disabled, calls `handle.enable()`, and asserts enabled. Compiled against the checkout's built core library without modifying the checkout. Exit 0. The same callback is used by registration; the protocol's Carrier transition is independently visible in the source.

Minimal remedy: use a weak callback that permanently prevents future enable transitions while preserving normal recorder flushing/draining. Do not misuse `mark_stopped`, which means the flush thread has already shut down. Add a regression that tries both enable APIs after an actual trim and confirms the recorder remains off. If explicit application enable is deliberately an override, document that override and stop describing the resulting recording limit as terminal; this is then a policy question rather than a bug.

## Questions and coverage limits

- **Default feature set cannot enforce a later stop for arbitrary profilers.** The `dial9` feature is optional/default off (`/tmp/dial9-manual-sampling-spike/dial9-sampling/Cargo.toml:16`). Without it, `SamplingStatus` exposes only frozen `enabled` (`/tmp/dial9-manual-sampling-spike/dial9-sampling/src/lib.rs:368`) and the protocol drops the recording receiver (`/tmp/dial9-manual-sampling-spike/dial9-sampling/src/protocol/engine.rs:387`). A custom profiler using that Boolean cannot receive terminal trims, although the worker moves membership to Carrier. The README does tell Dial9 users to enable registration. This is an integration-contract limitation, not a bug for registered Dial9 consumers. Either require registration for the soft-cap claim or provide an equally small generic stop registration hook if non-Dial9 profilers are supported.

- **Fast applications can disappear without membership evidence.** Admission returns after `tokio::spawn` without awaiting the first membership PUT (`/tmp/dial9-manual-sampling-spike/dial9-sampling/src/protocol/engine.rs:372`). An application can finish before that worker is scheduled; session cleanup cancels it and the biased cancellation branch wins before `worker.run()` (`engine.rs:373`). Even when membership is written, successful shutdown deletes it (`engine.rs:1022`), and the roster is a latest-state CAS object. This is critical to the parent's new post hoc population requirement: neither membership nor a trace from a sampled process currently supplies durable active-interval history. The API also does not expose invocation/rank/pool metadata to the recorder. Root is already investigating that requirement; lifecycle changes alone must not be presented as establishing historical identifiability.

- **Registrations retain small metadata/tasks for every recorder ever registered during the callback.** The weak recording reference correctly avoids retaining recorder buffers/workers, but each `register` appends a StopAction and monitor handle without pruning (`/tmp/dial9-manual-sampling-spike/dial9-sampling/src/registration.rs:63`). This is bounded for the normal one-recorder-per-application use; rotating/replacing a recorder repeatedly in a long-lived application grows metadata and pending monitors until callback cleanup. Optional follow-up: one stop monitor per registry and discard dead registrations, if that usage is supported. Do not inflate this change to solve an unsupported usage pattern.

## Sound portions / verification

- Runtime is owned before polling backend user code. Factory panic does not leave spawned async work alive indefinitely; shutdown uses the explicit cooperative/bounded policy.
- Application callback runs outside the entered sampling runtime, supports borrowed/non-Send futures and results, and owns application runtime teardown.
- Status drop/return does not own or extend runtime lifetime. Registry upgrades racing session cleanup are serialized by its closed flag; stop actions are idempotent and invoke the callback outside the lock.
- Recorder stop happens before bounded membership cleanup; storage errors preserve the recording choice and do not cause a late enable.
- Public tests cover callback success/error/panic, factory panic, entered-runtime rejection, returned status/recorder cleanup, fallback and borrowed values. Paused-time tests cover trim/outage behavior; Shuttle covers registration/cleanup and duplicate stop races.
